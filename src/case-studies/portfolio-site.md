## 의도

자주쓰이는 컴포넌트(아코디언/탭/모달/드롭다운/폼 검증/슬라이더)를 라이브러리 형태로 모아 경력 소개와 함께 담는 구조의 포트폴리오 사이트를 제작하고자 했다.
컴포넌트 6개 등 반복되는 구조(상세페이지, 라이브 데모, 문서)를 효율적으로 생성하는 템플릿 구조로 기획했다.

### 구현 과제

1. 클라이언트 프레임워크 없이 빌드타임에 정적 HTML을 생성해, 접근성·성능을 직접 통제할 수 있는 기술 스택
2. 컴포넌트 6개를 반복되는 구조(상세 페이지·라이브 데모·문서)로 효율적으로 생성하는 템플릿 구조
3. 라이트/다크 모드, 반응형 레이아웃
4. GitHub Pages 자동 배포

## 구현 과정

### 기술 스택 선택

정적 사이트 제너레이터로 11ty(Eleventy)를 선택했다. React 같은 클라이언트 프레임워크 대신 빌드타임에 순수 HTML을 생성하는 방식을 택한 이유는, 웹퍼블리셔라는 직무 자체가 마크업·접근성·성능을 직접 다루는 역할이라 프레임워크 런타임 없이 결과물을 그대로 통제할 수 있는 스택이 포트폴리오의 방향과 맞았기 때문이다. Nunjucks 템플릿과 레이아웃 체이닝(`layouts/base.njk` → `layouts/components.njk`)으로 컴포넌트 6개의 상세 페이지를 반복 없이 생성했고, 디렉터리 데이터 파일(`components.11tydata.js`)로 URL을 `/components/<slug>/`로 통일했다.

인터랙션은 transform/opacity 애니메이션에 강점이 있는 GSAP + ScrollTrigger로 구현했다. 색상 전환처럼 순수 CSS transition으로 충분한 부분(다크모드 등)에는 GSAP을 쓰지 않는다는 원칙을 세워, 두 방식을 용도에 맞게 나눠 썼다. 스타일은 Sass로 작성해 npm 스크립트(`sass` CLI + `concurrently`)로 빌드하도록 구성했다 — 지금 규모에서는 이 방식으로 충분하다고 판단했고, 나중에 필요해지면 11ty 자체 빌드 파이프라인에 통합하는 방향으로 확장할 수 있게 열어뒀다.

### 정보구조를 다시 설계한 과정

처음엔 컴포넌트 6개를 "케이스 스터디"라는 이름으로 소개했다. 그런데 미니프로젝트보다 이 포트폴리오 사이트가 먼저 공개되는 순서라는 걸 고려하면, "케이스 스터디"라는 이름은 낱개 UI 부품보다는 프로젝트 단위의 이야기에 더 어울렸다. 그래서 "컴포넌트 라이브러리" 형태로 이름과 구조를 다시 잡았다 — 목록 페이지도 텍스트 나열이 아니라 실제로 동작하는 라이브 미리보기 카드로 바꿨다.

문서 구조도 함께 정리했다. "문제 → 접근 및 시행착오 → 회고"라는 원래 구조는 겪은 과정을 있는 그대로 보여주기엔 좋았지만, 경력직 지원이라는 위치에서는 "시행착오"라는 표현이 자칫 아직 배우는 단계처럼 읽힐 위험이 있었다. "기획 → 구현 과정 → 결과"로 바꾸고, 서술도 "시도했다가 실패해서 바꿨다"보다 "이런 점을 고려해서 이렇게 설계했다"는 흐름으로 다시 썼다 — 같은 기술적 판단을 담되, 판단의 근거를 먼저 보여주는 쪽을 택했다. 지금 이 문서도 그 구조를 그대로 따른다.

### 컴포넌트를 "데모"가 아닌 재사용 가능한 조립 단위로 재설계

컴포넌트 라이브러리를 만들면서, 상세 페이지의 "라이브 데모"가 실제로는 그 페이지에서만 동작하는 전용 코드로 갇혀 있다는 걸 발견했다. 스타일은 `.component-demo--{slug}`라는 전시 페이지 전용 선택자 아래에서만 정의돼 있었고, 동작(JS)도 그 페이지에 한 번 심어지는 스크립트로 따로 작성돼 있어서, 같은 컴포넌트를 사이트 다른 자리로 그대로 옮겨 쓸 수 없는 구조였다. "컴포넌트는 언제 어디서든 조립해서 쓸 수 있어야 한다"는 애초의 취지와 어긋나는 부분이었다.

그래서 스타일을 세 단계로 다시 나눴다. 컴포넌트 자체 파일(`component.css`, `@use`/`@forward`로 컴포넌트별 파일 분리)에서 마크업 구조에 필요한 골격을 잡고, 그 안에서 사이트 디자인 토큰(`--color-accent` 등)을 바로 참조해 사이트 어디에 있든 1차 디자인이 완성되게 하고, 특정 위치에서만 필요한 디테일(`.career .accordion__item`처럼 부모 선택자로 범위를 좁히는 방식)은 그 자리의 스타일에서 오버라이드하도록 정리했다. 전시 페이지 전용 레이아웃(데모를 감싸는 박스 등)은 별도 파일로 분리해, "컴포넌트 자체의 스타일"과 "보여주기 위한 포장"을 구분했다. 사이트에서 실제로 쓰지 않는 컴포넌트는 그 파일만 지우면 라이브러리에서 빠지는 구조라, 계속 정리하기도 쉬워졌다.

JS도 같은 방향으로 다시 짰다. 페이지 로드 시 한 번 실행되고 끝나는 인라인 스크립트 대신, `setupX(selector)` 형태로 export하는 함수로 만들어 어디서든 같은 함수를 불러 초기화할 수 있게 했다. 다만 아코디언은 "그룹 안에서 하나만 열리는 방식"과 "각 항목이 독립적으로 열고 닫히는 방식"이 실무에서 둘 다 흔하게 쓰인다는 걸 확인해서, 어느 한쪽을 "기본"으로 정하고 다른 쪽을 예외로 취급하는 대신 `setupAccordionSingle`/`setupAccordionMultiple` 두 함수로 나란히 뒀다. 트리거-패널 매핑, ARIA 상태 갱신 같은 공통 로직은 한 곳에서 공유하고, "다른 패널을 닫을지 말지"라는 실제 동작 차이만 각 함수가 따로 갖는 구조다. 함수 이름도 새로 만들기보다 Radix UI, Syncfusion 등 여러 컴포넌트 라이브러리가 공통으로 쓰는 `single`/`multiple` 표기를 그대로 따라서, 처음 보는 사람도 이름만으로 바로 의도를 파악할 수 있게 했다.

### 접근성과 인터랙션 디테일

라이브 데모는 iframe이 아니라 실제 마크업을 페이지에 그대로 인라인으로 심어서, 스크린샷이 아니라 "진짜 동작하는 컴포넌트"라는 걸 보여주도록 구현했다. 헤더가 `position: sticky`라 앵커로 이동하면 대상 섹션 제목이 헤더에 가려지는 문제는 `scroll-padding-top`을 헤더의 실제 높이에 맞춰 동적으로 계산해 해결했다.

스크롤에 따라 요소가 살짝 올라오며 나타나는 GSAP ScrollTrigger 인터랙션은, 트리거 발동 지점이 "문서에서 스크롤 가능한 최대 위치"를 넘어버리면 그 요소가 영원히 나타나지 않는(그런데 클릭은 되는) 경우가 생길 수 있다는 걸 확인했다. 모든 트리거의 시작 지점을 수학적으로 항상 도달 가능한 값(`top 100%`)으로 통일해, 페이지 어디에 위치하든 안전하게 동작하도록 만들었다. 다크모드는 `data-theme` 속성과 CSS 커스텀 프로퍼티(디자인 토큰) 전환 방식으로 구현했고, 색상만 바뀌는 전환이라 GSAP 대신 순수 CSS transition으로 처리했다.

### 배포

GitHub Pages와 GitHub Actions로 배포 파이프라인을 구성했다. `main` 브랜치에 푸시하면 Actions가 자동으로 빌드해 배포하도록 해서, 별도 수동 배포 없이 콘텐츠 업데이트에만 집중할 수 있게 했다.

## 결과

- 11ty 기반 정적 사이트로, 프레임워크 런타임 없이 접근성·성능을 직접 통제할 수 있는 구조 완성
- 컴포넌트 6개를 라이브러리 형태로 소개하는 정보구조와, 프로젝트 단위 이야기를 위한 "케이스 스터디" 섹션을 분리해 확장 가능한 구조로 정리(다음 항목: 미니프로젝트)
- 데모 페이지 전용으로 갇혀 있던 컴포넌트 스타일/스크립트를, 골격(컴포넌트 파일) → 토큰(사이트 디자인 토큰) → 디테일(부모 선택자 오버라이드) 3단 계층과 재사용 가능한 `setupX()` 함수로 재설계해, 사이트 어디서든 조립해 쓸 수 있는 구조로 정리
- `scroll-padding-top`, ScrollTrigger 안전 발동 지점 등 스크롤 인터랙션 관련 접근성 이슈를 직접 발견하고 해결
- Sass 빌드 파이프라인 + GitHub Actions 자동 배포로 유지보수 가능한 구조 확보
