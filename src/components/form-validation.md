## 의도

회원가입 폼처럼 여러 필드가 있는 폼의 검증 시스템 제작. 제출 시 한 번만 검증하는 수준을 넘어서고자 했다.

### 구현 과제

1. 필드를 벗어날 때(blur) 검증하되, 너무 즉각적인 에러 표시로 사용자를 불안하게 만들지 않을 것
2. 한 번 검증(touched)된 필드는 이후 타이핑마다 실시간 재검증
3. `role="alert"`로 스크린리더에게 에러를 자동 안내
4. 필드가 늘어나도(이름/이메일/아이디/비밀번호/비밀번호 확인/자기소개 등) 매번 손으로 등록하지 않아도 되는 구조
5. 비밀번호 확인처럼 다른 필드 값과 비교해야 하는 크로스필드 검증
6. 제출 시 전체 필드 재검증 + 첫 에러 필드로 포커스 이동
7. 넓은 라이브 데모 박스부터 좁은 모달 안까지, 서로 다른 폭의 컨테이너 안에서도 안 넘치고 적정 폭을 유지할 것

## 구현 과정

### touched 상태 관리

"이미 검증했는지"(touched)는 DOM 속성에서 역으로 추론하지 않고 별도의 `hasBeenValidated` 불리언 변수로 명시적으로 관리했다. `aria-invalid`는 `null`/`'true'`/`'false'` 세 상태를 갖는데 `'false'`도 문자열이라 조건문에서는 truthy로 취급되므로, "한 번도 검증 안 한 상태"와 "성공 상태"를 이 속성만으로 구분할 수 없다. DOM 속성은 "지금 렌더링 결과"만 나타낼 뿐 "이력·과정" 정보는 별도 변수로 관리해야 한다는 원칙에 따른 설계다. 값을 비교할 때도 `getAttribute(name)`으로 읽은 문자열을 `=== 'true'`처럼 명시적으로 비교하는 방식을 일관되게 적용했다.

### 필드별 재사용 구조

필드마다 독립된 `isValid`/`hasBeenValidated`가 필요해, `setupFieldValidation({ input, errorEl, validate, ... })`이 `forceValidate` 함수를 반환하는 클로저 패턴으로 설계했다. 반환된 `forceValidate`는 자신을 만든 함수 스코프 안의 `input`/`errorEl`을 계속 참조할 수 있다는 클로저의 특성을 활용한 구조다.

### HTML5 내장 검증과 커스텀 규칙의 경계

`required`/`minlength`/`type="email"`처럼 "존재 여부·길이"로 표현 가능한 규칙은 HTML 속성에 위임하고, "영문 시작+숫자 조합", "8자 이상+특수문자 포함" 같은 구성 규칙은 정규식 기반 커스텀 `validate` 함수로 처리하는 하이브리드 구조로 정리했다. 정규식은 반드시 `.test(input.value)` 형태로 호출해 boolean 결과를 반환하도록 일관되게 작성했다 — 정규식 객체 자체는 항상 truthy이므로, 이 부분을 놓치면 검증이 사실상 무력화된다.

### 필드 자동 수집

필드마다 `setupFieldValidation(...)`을 손으로 호출하는 대신, `form.querySelectorAll('input, textarea')` + `forEach`로 자동 수집하고, `customRules[field.id]`로 필드별 예외 규칙만 등록하는 구조로 설계했다. 필드가 늘어나도 마크업에 `aria-describedby`로 연결된 에러 span만 추가하면 되는 구조다.

### 크로스필드 검증

`userPWconfirm`의 `validate`는 `userPW` 값과 비교하도록 구성했다. 두 필드가 모두 빈 값일 때 `'' === ''`로 "일치함"이 되지 않도록 `input.value.length > 0` 조건을 함께 걸었다.

```js
const validate = () => userPWconfirm.value.length > 0 && userPWconfirm.value === userPW.value;
```

"원본 비밀번호를 입력하는 도중에도 확인 필드까지 실시간 성공 표시가 뜨는 게 맞는가"는 여러 서비스를 조사해 판단했다. "원본 형식 통과"와 "확인 필드 일치 여부"를 서로 독립적으로 표시하는 게 실무에서 흔한 패턴임을 확인하고 지금 구조를 유지했다.

### 여러 폭의 컨테이너에 들어가는 레이아웃

이 폼은 컴포넌트 상세 페이지의 넓은 라이브 데모 박스, 홈의 단독 데모, 그리고 폼 모달(`.modal__body`, 상대적으로 좁음)까지 서로 다른 폭의 컨테이너 안에 그대로 재사용된다. 처음엔 `.form`에 폭 규칙이 전혀 없어 넓은 박스에서는 지나치게 늘어나 보였고, 좁은 모달에서는 반대로 비밀번호 확인처럼 인풋이 한 줄에 2개 있는 필드가 화면 밖으로 튀어나갔다. 튀어나가는 원인은 `.form__input-wrap`이 `display: flex`인 부모 안의 flex item인데 안의 `input`에 `width`가 지정된 적이 없어 브라우저 기본폭을 그대로 가졌기 때문이다 — flex item은 `flex-shrink`를 줘도 기본값 `min-width: auto` 때문에 자기 콘텐츠의 고유폭보다 안 줄어드는 스펙이라, `flex-shrink`만 줘서는 해결되지 않았다. `.form__input-wrap`과 `input`/`textarea` 양쪽에 `min-width: 0`을 명시하고, `.form` 자체에는 고정 `width` 대신 `width: 100%; max-width: 460px;`를 줘서 해결했다. 고정폭을 쓰면 모달처럼 더 좁은 부모 안에서 오히려 넘칠 수 있는데, `max-width` + `width: 100%`는 넓은 곳에선 460px로 캡되고 좁은 곳에선 그 폭에 자연히 맞춰 줄어든다. 하나의 컴포넌트가 여러 컨텍스트에서 재사용될수록, 스스로 최대 폭을 갖고 부모에 맞춰 줄어들 수 있게 만드는 편이 안전하다는 걸 확인한 경험이다.

### 제출 시 전체 검증

제출 시 전체 필드를 재검증해 첫 에러 필드로 포커스를 이동한다. 배열 인덱스 조회 결과가 `0`(첫 필드 실패)이거나 `-1`(모두 통과)일 수 있다는 점을 고려해, `if(okIndex)`처럼 값 자체의 참/거짓을 판단하지 않고 `okIndex !== -1`로 명시적으로 비교했다. `0`은 falsy, `-1`은 truthy라 값 자체로 판단하면 뜻이 반대로 뒤집히기 때문이다.

문법 오류 없이도 의도와 다르게 동작하는 코드(속성 비교, 정규식 반환값, falsy/truthy 판단, flex item의 최소 폭)는 눈에 잘 띄지 않는다. 검증 로직과 레이아웃 양쪽에 값과 크기를 명시적으로 다루는 습관을 일관되게 적용한 것도 그래서다.

## 결과

- HTML5 위임 + 커스텀 규칙 테이블 하이브리드 구조로, 필드 개수에 무관하게 확장 가능한 검증 시스템 완성
- blur 시 첫 검증, touched 이후 실시간 재검증까지 자연스러운 타이밍 설계
- 크로스필드 검증(비밀번호 확인) 반영
- 제출 시 전체 필드 강제 검증 + 정확한 falsy 판단으로 첫 에러 필드 포커스 이동
- `max-width` + `min-width: 0` 조합으로 넓은 데모 박스부터 좁은 모달까지 서로 다른 컨테이너에서 모두 안전하게 재사용
