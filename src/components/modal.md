## 의도

화면 전체를 덮는 모달 제작. 아코디언·탭과 달리 **포커스 관리**가 핵심 과제로 추가된다. 스크린리더/키보드 사용자 입장에서 모달이 열렸는데 포커스가 여전히 배경 페이지에 남아있으면, 화면 뒤에 숨겨진 콘텐츠를 계속 탐색하게 되는 접근성 문제로 이어지기 때문이다.

### 구현 과제

1. 마크업 (`role="dialog"`, `aria-modal`, `aria-labelledby`)
2. 열기/닫기 기본 동작
3. ESC로 닫기
4. 배경 클릭으로 닫기
5. 열릴 때 모달 안으로 포커스 이동, 닫힐 때 트리거로 복귀
6. Tab이 모달 밖으로 나가지 않도록 트랩
7. 다른 fixed/sticky 오버레이 요소(사이드 목차 등)와 같은 페이지에 있어도 항상 모달이 위에 그려지도록 쌓임 순서 관리

## 구현 과정

### 트리거 포커스 복귀

닫을 때 포커스를 되돌릴 트리거는 "지금 클릭된 요소"를 실시간으로 추적하는 대신, 모달을 여는 함수가 호출되는 시점에 인자로 직접 넘겨 확정하는 방식으로 설계했다. 배경(오버레이) 클릭으로 닫는 경로까지 고려하면, 오버레이 자신도 `.modal` 밖에 있는 요소라 실시간 추적 방식으로는 "지금 막 클릭된 것"이 오버레이 자기 자신으로 잘못 잡힐 여지가 있다. `tabindex`가 없는 `div`는 `.focus()`를 호출해도 반응하지 않으므로, "모달을 연 주체"라는 정보를 여는 시점에 고정해두는 편이 안전하다.

### 초기 포커스 대상

첫 포커스가 DOM 순서상 우연히 정해지지 않도록 신경 썼다. `modal-header`가 `modal-body`/`modal-footer`보다 마크업에서 먼저 나오는 구조라, focusable 요소 배열의 첫 항목을 그대로 쓰면 "닫기(X) 버튼"이 우연히 첫 포커스가 되어버린다 — 모달을 열자마자 다음 Tab이 닫기로 가는 건 직관과 어긋나고, 실수로 파괴적 액션에 가까운 버튼에 초반 포커스가 가는 것도 피하고 싶었다. WAI-ARIA APG 패턴을 참고해 **`tabindex="-1"`을 다이얼로그 제목에 부여**하고, 폼이 없는 모달(확인 모달 등)은 제목으로, 폼이 있는 모달은 첫 `input`으로 포커스를 이동시키는 구조로 정리했다. 이 방식은 스크린리더가 다이얼로그 역할과 제목을 먼저 안내해주는 효과도 함께 가져간다.

### 닫기 버튼의 시각적 위치와 탭 순서 분리

"X 버튼은 시각적으로 우측 상단에 두되, Tab 순서상으로는 맨 마지막이었으면 좋겠다"는 요구를 반영해야 했다. 탭 순서는 DOM 순서를 따르고 시각적 위치(CSS `position: absolute`)와는 무관하다는 원리에 따라, 양수 `tabindex`로 순서를 강제하는 방법은 페이지 전체의 탭 흐름을 예측 불가능하게 만들 위험이 있어 배제했다. 대신 focusable 목록 자체를 재정렬하는 함수로 감싸는 방향을 택했다.

### 포커스 트랩의 경계 처리

포커스 트랩은 경계(첫 요소/마지막 요소)에서만 개입하고 중간 이동은 브라우저 기본 동작에 맡긴다는 원칙으로 설계했다. Tab은 마지막 요소에서 첫 요소로, Shift+Tab은 첫 요소에서 마지막 요소로 순환해야 하므로, `e.shiftKey` 값에 따라 두 방향을 정확히 구분하는 조건을 뒀다.

```js
if (!e.shiftKey && document.activeElement === last) {
  e.preventDefault();
  first.focus();
} else if (e.shiftKey && document.activeElement === first) {
  e.preventDefault();
  last.focus();
}
```

### 비동기 처리가 필요한 지점과 아닌 지점

`requestAnimationFrame`이 필요한 경우와 아닌 경우를 구분하는 기준을 세웠다. 포커스 이동은 `classList.add`처럼 동기 연산 다음 줄에서 이미 최신 상태가 반영돼 있으므로 rAF로 감쌀 이유가 없다. 오히려 불필요하게 감싸면, 모달을 열자마자 아주 빠르게 닫는 경우 rAF 콜백이 닫힌 뒤에 실행되며 이미 사라진 모달의 제목으로 포커스를 다시 뺏어가는 레이스 컨디션이 생길 수 있다. 반대로 `display: none → flex`와 `width: 0 → 500px`를 같은 클래스 토글로 동시에 적용하는 트랜지션은 다르다. `display: none`인 요소는 렌더 트리에 존재하지 않아 브라우저가 "시작 상태(width: 0)"를 한 번도 페인트한 적이 없어, 전환할 이전 프레임 자체가 없다. 이 경우엔 rAF로 한 프레임을 넘겨 display 전환과 width 전환 사이에 브라우저가 그릴 시간을 확보해야 트랜지션이 실제로 동작한다. 같은 API라도 "이미 렌더링된 요소의 상태 변경"과 "렌더링 자체가 시작되지 않은 요소의 애니메이션 시작점 만들기"는 다른 문제라는 기준으로 구분해 적용했다.

### 숨김 처리 방식의 트레이드오프

모달을 숨길 때 `display:none` 대신 `opacity + visibility`를 쓰면 트랜지션이 가능해지는 대신, 요소가 렌더 트리에 남아 레이아웃 계산 대상이 된다는 점을 함께 검토했다. 다만 모달 오버레이는 `position: fixed/absolute`로 일반 문서 흐름에서 이미 빠져 있어 다른 요소의 레이아웃에 영향을 주지 않고, `visibility: hidden`이 포커스/스크린리더 접근도 함께 차단해주므로, 소수의 모달을 다루는 지금 규모에서는 실용적인 선택이라고 판단했다.

### z-index:auto와 DOM 순서 — 목차 위에 모달이 뜨지 않던 버그

`.modal`이 `position: fixed; inset: 0;`으로 화면 전체를 덮게 만들었는데, 정작 z-index를 명시하지 않아 `z-index: auto` 상태였다. 같은 페이지의 사이드 목차(`position: sticky`)도 z-index가 없어 마찬가지로 auto였는데, 이렇게 둘 다 z-index:auto인 상태에서 포지션만 잡은 요소는 값 비교가 아니라 **DOM 트리 순서**로 쌓인다. 목차를 담은 요소가 모달을 담은 요소보다 마크업에서 나중에 나와서, 모달을 열어도 목차가 항상 그 위에 그려지는 문제가 있었다. 미리 정의해둔 `--z-overlay` 오버레이 전용 z-index 토큰을 `.modal`에 명시적으로 적용해 DOM 순서와 무관하게 항상 모달이 위에 그려지도록 고쳤다. `position`만 주고 z-index를 안 주면 값 비교가 아니라 DOM 순서로 쌓인다는 점은, 겹칠 수 있는 오버레이 요소를 늘릴 때마다 다시 떠올려야 할 원칙으로 남겨둔다.

### focusable 목록 캐싱

`focusTrap`이 Tab을 누를 때마다 `activeModal.querySelectorAll(focusAbles)`를 다시 실행할 필요는 없다고 판단했다. 모달이 열려있는 동안(정적 마크업이라 내용이 바뀌지 않는 상황)에는 DOM을 매번 다시 훑을 이유가 없기 때문이다. 모달이 열리는 시점에 한 번만 구해 변수에 캐싱하고, `focusTrap`은 그 캐시만 참조하도록 설계했다. `openModal`에서 첫 포커스 대상(input/select 등)을 찾을 때도 별도로 `querySelector`를 다시 호출하지 않고, 캐싱해둔 배열을 `Array.prototype.find()`로 조회해 같은 소스를 공유하게 했다. 이 과정에서 캐싱 값을 `Array.from(...)` 결과 하나로 통합해 중복 변수를 정리했다.

### 다른 컴포넌트와 조합 — 폼 모달

실제 서비스에서 모달은 결국 다른 컴포넌트를 담는 그릇으로 쓰이는 경우가 많다는 점을 보여주기 위해, 항상 펼쳐진 채로만 보여주는 정적 프리뷰(`.modal--static`, 상호작용 없이 `aria-hidden`으로 감춘 미리보기)와는 별도로, 실제로 열고 닫히며 안에 폼 검증 컴포넌트를 그대로 조립한 "폼 모달" 데모를 추가했다. 같은 폼검증 컴포넌트가 홈의 단독 데모와 폼 모달 양쪽에 동시에 렌더링되므로, `id`가 겹치지 않도록 필드 id에 접미사를 주는 옵션(`idSuffix`)을 폼검증 쪽에 미리 열어두고 재사용했다 — 컴포넌트를 서로 조합할 때는 각자 독립적으로 동작할 때는 드러나지 않던 id 충돌 같은 문제가 새로 생길 수 있다는 걸 확인한 경험이다.

### 확장성 검토 — 셸(shell) + 동적 주입 패턴

실제 서비스처럼 모달 종류가 수십 개로 늘어나는 상황을 가정하면, 지금처럼 모달마다 정적 HTML을 미리 준비해두는 방식은 관리 비용이 커진다. 대안으로 **모달 컨테이너(셸)는 하나만 두고, 제목/본문/푸터를 열 때마다 데이터 기반으로 동적 주입**하는 패턴을 검토했다. 이 구조에서는 포커스 트랩 로직이 오히려 단순해지고(대상이 항상 셸 하나), "focusable 목록을 캐싱하면 안 되는 이유"도 더 분명해진다(내용이 매번 달라지므로). 브라우저 네이티브 `<dialog>` 요소(top layer 렌더링, ESC/backdrop 기본 지원)도 대안으로 함께 검토했다. 제공된 예시 코드를 그대로 신뢰하지 않고 직접 검증하는 과정에서, 예시에도 있던 동일한 첫 포커스 이슈를 함께 확인하고 반영했다.

## 결과

- 키보드만으로 완전히 조작 가능한 모달 (Tab 순환, ESC 닫기, 배경 클릭 닫기, 트리거로 포커스 복귀)
- `role="dialog"` + `aria-modal` + `aria-labelledby`/`aria-describedby`로 스크린리더 컨텍스트 제공
- 포커스 트랩에서 경계(첫/마지막 요소)에서만 개입하고 나머지는 브라우저 기본 동작에 맡기는 최소 개입 원칙 적용
- 폼 유무와 무관하게 일관된 초기 포커스 처리 (`tabindex="-1"` + 다이얼로그 제목)
- `--z-overlay` 토큰 적용으로 다른 sticky/fixed 요소와 무관하게 항상 모달이 최상단에 렌더링
- 폼검증 컴포넌트를 그대로 조립한 폼 모달로, 컴포넌트를 조합해 쓸 때의 id 충돌 관리까지 확인
